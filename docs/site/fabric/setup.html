Setup walkthrough

From a clean Fabric workspace to a data agent answering grounded questions, in about thirty minutes on a small demo corpus. Everything runs inside your Fabric tenant — both the storage and the query-time embedding model. No Azure OpenAI, no third-party vector database.

What you're setting up, in one paragraph

A knowledge model (a .rlat file) is a pre-computed semantic index of a folder of source files — your team docs, an API reference, whatever. It stores text chunks (passages) together with the numeric vector (embedding) each one maps to under a fixed embedding model. The deploy step in this walkthrough takes the .rlat out of OneLake storage and into a Fabric Eventhouse KQL database — the storage shape that the query-time search function will read from. Deploy alone doesn't make the corpus answerable yet: the search function (Step 3) and the data agent (Step 4) ride on top and land in later phases. Once all five steps are in place, a Fabric data agent or external LLM client can ask "what does this corpus say about X?", get back the relevant passages with citations into the source files, and answer from those passages rather than guessing.

Before you start

  • A Microsoft Fabric workspace at F2 capacity or higher. F2 is enough for the deploy step on a small demo corpus (~100 to ~1,000 passages). Step 3 (the sandbox embedding function, coming in a later phase) uses the Eventhouse Python plugin — capacity-policy permitting on F2 — and may need an SKU bump for production loads. We'll re-state the SKU guidance when Step 3 lands.
  • Workspace permissions: you (or the service principal you'll use) need Admin or Member on the workspace. Service principal setup is covered in Microsoft's Fabric API SP guide; the SP needs the workspace role plus Fabric API tenant-setting access enabled by your Fabric admin.
  • A default lakehouse in the workspace. The data-agent integration reuses your existing lakehouse — no need to create a new one.
  • A local checkout of the public resonance-lattice-cli repository if you want to run the one-shot provisioning script from your laptop. Otherwise the same steps are doable in the Fabric portal.

Your workspace ID is the GUID in the portal URL when you're inside a workspace (https://app.fabric.microsoft.com/groups/<workspace-id>/…), or in Workspace settings → About.

Step 1 — Build a knowledge model

Coming in a later phase. For now use the existing fabric_build.ipynb notebook (in your workspace's notebooks/examples/) to build a .rlat from a folder of source files. The notebook writes the result to Files/rlat/<your-corpus-name>.rlat inside your default lakehouse.

Step 2 — Deploy the knowledge model

"Deploy" means taking your .rlat file out of OneLake storage and ingesting its passages + embeddings into a queryable KQL database table. The data agent (Step 4) talks only to KQL; nothing else reads the .rlat at query time.

What gets created

One Eventhouse item and its default KQL database, both called rlat-data-agent, alongside whatever else lives in your workspace. Inside that database:

  • passages_raw — an append-only table holding one row per passage with text, source location, content hash, and the 768-dimensional embedding. The vector column is stored under Fabric's Vector16 encoding policy (compact half-precision storage, accelerated cosine similarity).
  • passages — a materialised view over passages_raw that keeps only the most recent row per content_hash. This is the queryable surface the data agent reads. The view is incrementally maintained — new rows in _raw are folded in automatically; you don't run anything to refresh it.

Why two objects instead of one? KQL has no row-level upsert (update-or-insert). The append-only base plus most-recent-wins materialised view is the standard idiom: every deploy unconditionally appends to passages_raw, and the view dedupes lazily on content_hash. Re-deploying the same corpus is safe — the queryable row count stays at the number of distinct passages no matter how many times you run the deploy.

2a — Provision the Eventhouse and KQL database

One-time setup per workspace. Two options:

Option A — from a local checkout

Set three environment variables for your service principal (the project uses FABRIC_* names rather than AZURE_*): 

FABRIC_TENANT  = your tenant id
FABRIC_CLIENT  = service principal app id
FABRIC_SECRET  = service principal secret

Then from the repo root:

python scripts/fabric_e2e_provision_eventhouse.py \
    --workspace <your-workspace-id>

The script is idempotent — re-running prints the existing item ids without recreating. Copy the four values it prints (kqlDatabaseId, kqlDatabaseName, queryServiceUri, ingestionServiceUri) — you need them in Step 2b.

Option B — from the Fabric portal

  1. In your workspace, click + New item → Eventhouse.
  2. Name it rlat-data-agent; click Create.
  3. Open the Eventhouse → the default KQL database appears in the left pane (same name).
  4. In the database's Database details pane copy Query URI (this is the CLUSTER_URI parameter in the next step) and Data ingestion URI (the INGEST_URI parameter).

2b — Run the deploy notebook

The deploy notebook (fabric_deploy.ipynb) reads your .rlat from OneLake and ingests it into passages_raw. The materialised view rebuilds itself in the background; the whole thing is one notebook, runnable any time you want to refresh.

Get the notebook into your workspace one of two ways:

  • From a local checkout: from the repo root, python scripts/fabric_e2e_run_deploy_notebook.py --workspace <your-workspace-id> uploads the notebook and triggers a run with parameters set automatically.
  • From the portal: click + New item → Notebook, then Import notebook, and upload notebooks/examples/fabric_deploy.ipynb from a local checkout of the repo. Open the new notebook in the workspace and use it directly.
  1. Open the notebook in the workspace.
  2. In the Parameters cell, set:
    • KM_NAME — the basename of your .rlat (e.g. "team-docs" if the file is Files/rlat/team-docs.rlat).
    • KQL_DATABASE_NAME — defaults to "rlat-data-agent".
    • CLUSTER_URI and INGEST_URI — paste the values from Step 2a (or 2b's Query URI and Data ingestion URI).
  3. Run all cells. On a 100-passage corpus the whole notebook takes about a minute; first ingest becomes queryable within ~30 seconds of the queued upload.

The final cell prints a summary like: 

{
  "km_name":                   "team-docs",
  "kql_database":              "rlat-data-agent",
  "rows_ingested":             97,
  "passages_raw_before":       0,
  "passages_raw_after":        97,
  "passages_view_count":       97,
  "ingest_to_visible_seconds": 32.4,
  "ingest_source_id":          "08d54ac0-c0aa-4676-940d-00f4d1549caf"
}

If passages_view_count equals the passage count in your .rlat, deploy worked.

How to verify in the portal

  1. Open your Eventhouse → click into the rlat-data-agent KQL database.
  2. In the Explore your data query window, run: 
    passages
| count
    The number you see is the count of distinct passages from the latest deploy.
  3. Run passages | take 5 to spot-check a few rows.

Refreshing

Re-run the deploy notebook any time the underlying corpus changes. Re-deploys append to passages_raw; the materialised view keeps the count at the distinct-passage total. Capacity cost on a refresh that ingests the full corpus again is dominated by the initial queued ingest — under 50 CU-seconds for a 100-passage corpus, scaling roughly linearly with passage count.

If it doesn't work

The deploy notebook's per-cell errors are visible in the portal: open the notebook, switch to Run history, click the failed run, click the failed cell. The Fabric REST API does not (yet) surface per-cell errors, so this portal step is the only way to read the underlying exception.

Top three things that go wrong:

  • "Database not found" / 401 on the first DDL call — the SP doesn't have permissions on the KQL database. Open the database in the portal, Manage permissions → Add, give your SP Database Admin.
  • Ingest queued but passages_raw_after stays at 0 — Fabric's queued-ingest batching window is up to a few minutes on a cold Eventhouse. Wait, then run passages_raw | count in the KQL portal. If still zero after 5 minutes, check .show ingestion failures for the table.
  • FileNotFoundError on Files/rlat/… — the KM_NAME parameter doesn't match a .rlat file in your default lakehouse's Files/rlat/ folder. Browse the lakehouse in the portal, copy the exact basename, retry.
