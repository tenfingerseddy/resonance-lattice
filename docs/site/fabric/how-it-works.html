How it works (technical)

A plain-language walk through the mechanism. The point of the page is to make it clear why the design is shaped the way it is — in particular why retrieval happens in three layers and why none of the three layers calls an external service.

Phase 2 build

This page is filled in phase by phase. The "Retrieval inside Fabric" section below is the live content as of phase 2; the sections after it land with their phases.

What happens when you ask the data agent a question

A user types a question into the Fabric data agent. The agent decides, based on its instructions, that this question is one rlat's knowledge model can answer. Behind the scenes it generates a KQL query that calls rlat_search(), a stored function on the rlat-data-agent KQL database. The function:

  1. Turns the user's question into a 768-dimensional vector (the "embedding") using the same neural network the knowledge model was built with.
  2. Runs a cosine-similarity comparison against the passages table — the materialised view holding every passage's pre-computed embedding.
  3. Returns the top-k passages along with their source-file citations.

The data agent reads those passages, composes a natural-language answer, and shows them as citations to the user. If no passage is relevant enough (the top score is below a threshold), the agent refuses to answer rather than guess.

Retrieval inside Fabric — the sandbox embed

Step 1 above ("turn the question into a vector") is the part of rlat that's hardest to fit into a Fabric-native architecture. Most retrieval systems call an embedding API hosted somewhere else — OpenAI, Azure OpenAI, a self-hosted service — but that means data leaves the tenant and the call adds latency, cost, and a third-party dependency.

rlat avoids all three by running the embedding model inside the Fabric Eventhouse, using the Eventhouse's Python plugin sandbox. The sandbox is a small Python 3.11 environment that runs as part of a KQL query — same process, same security context, same capacity-billing meter as every other KQL query you run. Nothing leaves the tenant. There is no Azure OpenAI subscription to set up, no embedding-endpoint URL to configure, no second auth surface.

What's actually in the sandbox

Five artefacts ship into OneLake the first time you set up rlat in your workspace, at Files/rlat/encoder/:

  • The encoder weights — the trained gte-modernbert-base model as an ONNX file (~600 MB across model.onnx + the external-weights sibling model.onnx.data). Same file the local rlat CLI uses, pinned to a specific HuggingFace revision so every workspace gets bit-identical behaviour.
  • The tokenizer config (tokenizer.json, ~4 MB) — how text gets split into the tokens the model can see.
  • The HuggingFace tokenizers wheel (tokenizers-0.22.1-cp39-abi3-manylinux_2_17_x86_64.manylinux2014_x86_64.whl, ~3 MB). The Eventhouse Python sandbox image doesn't include this package out of the box; we ship the wheel and install it at query time. The slm_embeddings_fl() reference function does the same thing for the smaller e5 model — same pattern.
  • A newer ONNX runtime wheel (onnxruntime-1.20.1-cp311-cp311-manylinux_2_27_x86_64.manylinux_2_28_x86_64.whl, ~13 MB). The sandbox image ships onnxruntime 1.17.3 (Feb 2024), which is too old to load IR-10 ONNX models exported by recent PyTorch versions. Shipping a 1.20.1 wheel and importing onnxruntime after the install puts the newer copy first on sys.path for the rest of the query.

OneLake-hosted artefacts in the same tenant bypass the Eventhouse callout policy that ADX requires for arbitrary blob URLs — the OneLake auth + the ;impersonate URL suffix is the access check. So there's no extra cluster-admin step to permit the encoder download.

What embed_query() does, line by line

The embed_query() function is a tiny KQL wrapper around a python() evaluator. The Python block (running inside the sandbox) does five things:

  1. Install the tokenizers wheel via sandbox_utils.Zipackage.install(...). About 1–2 seconds. The sandbox caches the wheel content across queries on the same node, so subsequent calls skip the download.
  2. Load the tokenizer (Tokenizer.from_file('tokenizer.json')).
  3. Load the ONNX session (onnxruntime.InferenceSession('model.onnx', providers=['CPUExecutionProvider'])). The data-file sibling resolves automatically by the relative path baked into the .onnx graph.
  4. Tokenise the query and run the model. The output's first token (the CLS position) is the passage-level embedding.
  5. L2-normalise the vector so cosine similarity becomes a plain dot product. Return it as a dynamic column for KQL to join against.

Why the answer is the same as the local rlat CLI

Every step of the sandbox embed mirrors the corresponding step in the local field/encoder.py path that builds the knowledge model. Same ONNX revision; same tokenizer.json; same CLS-pool + L2-normalise. Bit-exactness isn't guaranteed (CPU vs sandbox runtimes may apply different graph fusions), but the G1 parity gate is the explicit hard floor: for a fixed set of test strings, cosine(sandbox_vec, local_vec) must be ≥ 0.999. If it's not, the deploy is broken; the deployment thesis doesn't hold; we stop and look at what diverged.

Capacity and latency

Measured on the F2 test workspace (one workspace, one cluster), with the live embed_query() function over 10 fixed test strings:

  • Cold first call — ~21 s. This includes sandbox spin-up, OneLake artefact fetch (5 files, ~615 MB total), wheel install, tokenizer and ORT session init.
  • Warm calls — ~13–22 s, mean ~19 s. The sandbox is single-use per query (a new Python process every call), so the ORT session is reloaded each time even though the OneLake artefacts are cached per-node.

These are above the 2–4 s figure originally hoped for. The Phase 6 semantic cache short-circuits repeated paraphrased questions and mostly moots steady-state latency for the question shapes the data agent actually sees in production. Latency optimisation beyond that is parked for a later phase if measurements on a real-traffic deployment show the cache isn't enough.

What rlat_search() does (next phase)

The learning layer (later phase)

Phase 6 + Phase 7 add the insight layer: a separate row type in passages holding cached, cited answers generated by a periodic consolidation job from past queries. The data agent searches sources and insights together, so repeated paraphrased questions hit the cache. This page extends with that detail when the phases land.
